Project 01 · Backend

AWS Task Manager API

A FastAPI + SQLAlchemy task manager designed to deploy cleanly to AWS. The same code path runs on SQLite locally and PostgreSQL on RDS in production; S3 attachments are opt-in via a feature flag. Comes with a Dockerfile, GitHub Actions CI, and least-privilege IAM policies committed in the repo.

FastAPI SQLAlchemy 2.0 PostgreSQL / SQLite boto3 (S3) Docker EC2 + RDS + S3 IAM
GitHub ↗
01 · Architecture

Stateless FastAPI service on EC2, talking to a Postgres database on RDS, and (optionally) S3 for file attachments. The same code runs locally against SQLite with S3 disabled.

in-repo code external service highlighted in the flow below
02 · Key files

The whole repo is intentionally small. Five files do the work; the rest is config, tests, and deployment docs.

app/main.py
FastAPI app construction, lifespan that calls init_db() on boot, exception handlers, router mounting. The narrowest possible entrypoint.
app/database.py
SQLAlchemy engine + sessionmaker. Reads DATABASE_URL from env so the same code runs against SQLite, local Postgres via Docker, or RDS Postgres.
app/models.py
The Task ORM model with a TaskStatus enum, UUID primary keys, and timestamps with automatic update tracking via SQLAlchemy 2.0 typed columns.
app/routers/tasks.py
The REST endpoints — POST / GET / PUT / DELETE on /tasks plus /tasks/{id}/attachment for S3 uploads. Returns 404 / 422 / 503 with friendly bodies.
app/storage/s3.py
Optional S3 client wrapper. Feature-flagged via S3_ENABLED. Builds keys under a tasks/<id>/ prefix so the IAM policy can scope tightly.
iam/s3-task-attachments-policy.json
Real least-privilege IAM policy committed alongside the code. Grants GetObject / PutObject / DeleteObject on bucket/tasks/* only — no wildcards.
03 · Flow · create a task

Walks one POST request through the code — header parses, validation hits, model gets persisted, response returns. Use Step / Reset to advance the highlight on the diagram above.

step 0 / 5
1

Client sends the request

curl -X POST https://api.example/tasks with a JSON body of {title, description, status}. Travels over HTTPS to the load balancer.

2

ALB forwards to the EC2 app

The ALB terminates TLS and routes to the FastAPI container running on the EC2 instance, port 8000. Healthchecks at /health verify the instance is up.

3

FastAPI parses + validates

The route handler in routers/tasks.py receives the body. Pydantic's TaskCreate schema validates required fields and types, returning 422 with field-level errors if anything is off.

4

SQLAlchemy persists the row

Depends(get_db) hands the handler a request-scoped session. crud.create_task instantiates a Task with a new UUID, adds, commits, and refreshes. psycopg writes to RDS.

5

201 Created flows back

The handler returns the model serialized through TaskRead. FastAPI sets 201, the session closes in the dependency's finally, and the client receives JSON with the new task and its UUID.

Project 02 · Distributed systems

Distributed Job Queue System

A producer/worker pattern with SQS as the queue and DynamoDB as the state store. The API submits jobs in milliseconds and returns; the worker handles them out of the request path. Idempotency through a GSI, bounded retries, dead-letter on terminal failure, and an in-memory fallback so the whole system runs locally with zero AWS credentials.

SQS DynamoDB FastAPI boto3 CloudWatch moto (tests) Idempotency · Retries · DLQ
GitHub ↗
01 · Architecture

The API and worker are two independent processes. They communicate only through SQS messages and shared state in DynamoDB — no shared memory, no direct calls. That decoupling is the whole point.

in-repo process AWS service highlighted in the flow below
02 · Key files

Every external concern (queue, store) is an interface with two implementations. The worker uses only the abstract types, so the same code runs against in-memory fakes in tests and real SQS / DynamoDB in production.

app/routers/jobs.py
The producer endpoints — POST /jobs, GET /jobs, GET /jobs/{id}. Idempotency lookup happens here via the DynamoDB GSI before any SQS write.
app/queue/sqs_client.py
The QueueClient SQS implementation. Wraps send_message, receive_message, and delete_message. Paired with an in-memory implementation for tests.
app/store/dynamodb_store.py
The JobStore DynamoDB implementation. Owns the partition-key choice (UUID job_id), GSI query for idempotency keys, and update expressions for state transitions.
worker/runner.py
The poll loop: long-poll SQS → mark in_progress → run the handler → mark completed or failed → delete the message. Retry logic and DLQ handling live here.
app/job_processing.py
The pure handler functions (echo, sleep, fail, factorial). No I/O. Trivially unit-testable, easy to extend with new job types.
tests/test_sqs_dynamodb.py
End-to-end test against moto-mocked SQS + DynamoDB. Exercises the real boto3 code paths — same calls that run in production, just hitting moto's in-memory implementations.
03 · Flow · submit and process a job

One full job lifecycle — from the client's POST through the queue, into the worker, back to the client polling GET /jobs/{id} and seeing completed.

step 0 / 6
1

Client POSTs to /jobs

Body: {"type": "factorial", "payload": {"n": 10}, "idempotency_key": "abc"}. FastAPI validates with Pydantic.

2

Idempotency check (GSI query)

Producer queries the idempotency_key-index GSI. If a row exists with that key, the existing job_id is returned and the request becomes a no-op replay. Otherwise it continues.

3

Persist + enqueue

Producer PutItems a new row to DynamoDB with status pending and the payload, then SendMessages {job_id} to SQS. Returns 202 Accepted with the new job_id.

4

Worker pulls the message

The long-poll ReceiveMessage returns the job_id. SQS sets a 60-second visibility timeout — if the worker crashes mid-process, the message reappears.

5

Process + update state

Worker GetItems the row, marks in_progress, runs the handler in job_processing.py, then UpdateItems the row with completed + result JSON.

6

Delete the message

On success the worker DeleteMessages by receipt handle. Client now polls GET /jobs/{id} and gets status: completed, result: {...}. On failure, retry count bumps; after the cap, the message lands in the DLQ.

Project 03 · Frontend

React Task Manager Dashboard

A React + Vite dashboard that consumes the AWS Task Manager API end to end — the front half of a full-stack story. Six small components, an axios service layer that normalizes every HTTP error to a friendly message, env-driven backend URL, accessibility-first selectors, and 27 Vitest + React Testing Library tests across three boundaries (App, components, service).

React 18 Vite 6 JavaScript axios Vitest React Testing Library Responsive CSS · a11y
GitHub ↗
01 · Architecture

Three layers: App owns state, components are presentational + lightly stateful, services/api.js is the only place that knows about HTTP. The backend is the same FastAPI service from project 01.

in-repo module browser / backend highlighted in the flow below
02 · Key files

App is the only stateful piece. Components stay small and dumb. The service layer is the firewall between the rest of the app and HTTP.

src/App.jsx
Owns tasks, filter, loading, error. Computes visibleTasks and counts with useMemo. Fetches once on mount via useEffect. Handlers update state in place after each service call.
src/services/api.js
Axios instance bound to VITE_API_BASE_URL. The tasksApi wrapper throws normalized Error instances — network failures become "could not reach the API," backend 4xx surfaces the detail string.
src/components/TaskForm.jsx
Controlled inputs for title + description, client-side trim + validation, surfaces backend errors via local state. The only "smart" form in the app.
src/components/TaskItem.jsx
One row: checkbox toggle, inline edit mode (with its own draft state), delete. Tracks busy locally so buttons disable during the API call.
src/components/FilterBar.jsx
Three buttons with aria-pressed + count badges. Pure component, gets value and onChange from App. Tests assert on accessibility attributes, not CSS.
tests/App.test.jsx
15 integration tests against the real App with vi.mock('../src/services/api.js'). Covers initial render, filtering, create, toggle, delete, error banner, retry — all via accessibility selectors.
03 · Flow · toggle a task to done

A short user interaction traced from a checkbox click all the way to the backend PUT and back. Shows where state lives at each step.

step 0 / 5
1

User clicks the checkbox

The checkbox lives inside TaskItem.jsx. The onChange fires handleToggle, which calls the onToggle prop handed down from App. Local busy state flips to true; the row visually disables.

2

App.handleToggle decides the next status

App reads the current task's status. If it's done it'll flip to pending, otherwise done. Then it asks the service to persist that change.

3

tasksApi.update fires

The service layer issues http.put('/tasks/{id}', { status }). Any failure here is caught in App and surfaced via the ErrorBanner — the row stays at its old status, the user can retry.

4

Backend updates the row

FastAPI applies the partial update through SQLAlchemy, commits, returns the updated Task JSON. axios resolves the promise back in the browser.

5

State replaces the row

App's handler maps over tasks and swaps in the updated row. React re-renders TaskItem with the new status; the checkbox is now checked, the title gets the strike-through class. Counts on FilterBar update automatically via useMemo.
