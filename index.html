Project 01 · Backend

AWS Task Manager API

A FastAPI + SQLAlchemy task manager designed to deploy cleanly to AWS. The same code path runs on SQLite locally and PostgreSQL on RDS in production; S3 attachments are opt-in via a feature flag. Comes with a Dockerfile, GitHub Actions CI, and least-privilege IAM policies committed in the repo.

FastAPI SQLAlchemy 2.0 PostgreSQL / SQLite boto3 (S3) Docker EC2 + RDS + S3 IAM

01 · Architecture

Stateless FastAPI service on EC2, talking to a Postgres database on RDS, and (optionally) S3 for file attachments. The same code runs locally against SQLite with S3 disabled.

in-repo code external service highlighted in the flow below
02 · Key files

The whole repo is intentionally small. Five files do the work; the rest is config, tests, and deployment docs.

app/main.py
FastAPI app construction, lifespan that calls init_db() on boot, exception handlers, router mounting. The narrowest possible entrypoint.
app/database.py
SQLAlchemy engine + sessionmaker. Reads DATABASE_URL from env so the same code runs against SQLite, local Postgres via Docker, or RDS Postgres.
app/models.py
The Task ORM model with a TaskStatus enum, UUID primary keys, and timestamps with automatic update tracking via SQLAlchemy 2.0 typed columns.
app/routers/tasks.py
The REST endpoints — POST / GET / PUT / DELETE on /tasks plus /tasks/{id}/attachment for S3 uploads. Returns 404 / 422 / 503 with friendly bodies.
app/storage/s3.py
Optional S3 client wrapper. Feature-flagged via S3_ENABLED. Builds keys under a tasks/<id>/ prefix so the IAM policy can scope tightly.
iam/s3-task-attachments-policy.json
Real least-privilege IAM policy committed alongside the code. Grants GetObject / PutObject / DeleteObject on bucket/tasks/* only — no wildcards.
03 · Flow · create a task

Walks one POST request through the code — header parses, validation hits, model gets persisted, response returns. Use Step / Reset to advance the highlight on the diagram above.

step 0 / 5
1

Client sends the request

curl -X POST https://api.example/tasks with a JSON body of {title, description, status}. Travels over HTTPS to the load balancer.

2

ALB forwards to the EC2 app

The ALB terminates TLS and routes to the FastAPI container running on the EC2 instance, port 8000. Healthchecks at /health verify the instance is up.

3

FastAPI parses + validates

The route handler in routers/tasks.py receives the body. Pydantic's TaskCreate schema validates required fields and types, returning 422 with field-level errors if anything is off.

4

SQLAlchemy persists the row

Depends(get_db) hands the handler a request-scoped session. crud.create_task instantiates a Task with a new UUID, adds, commits, and refreshes. psycopg writes to RDS.

5

201 Created flows back

The handler returns the model serialized through TaskRead. FastAPI sets 201, the session closes in the dependency's finally, and the client receives JSON with the new task and its UUID.

Project 02 · Distributed systems

Distributed Job Queue System

A producer/worker pattern with SQS as the queue and DynamoDB as the state store. The API submits jobs in milliseconds and returns; the worker handles them out of the request path. Idempotency through a GSI, bounded retries, dead-letter on terminal failure, and an in-memory fallback so the whole system runs locally with zero AWS credentials.

SQS DynamoDB FastAPI boto3 CloudWatch moto (tests) Idempotency · Retries · DLQ
Reliability notes ↗ GitHub ↗
01 · Architecture

The API and worker are two independent processes. They communicate only through SQS messages and shared state in DynamoDB — no shared memory, no direct calls. That decoupling is the whole point.

in-repo process AWS service highlighted in the flow below
02 · Key files

Every external concern (queue, store) is an interface with two implementations. The worker uses only the abstract types, so the same code runs against in-memory fakes in tests and real SQS / DynamoDB in production.

app/routers/jobs.py
The producer endpoints — POST /jobs, GET /jobs, GET /jobs/{id}. Idempotency lookup happens here via the DynamoDB GSI before any SQS write.
app/queue/sqs_client.py
The QueueClient SQS implementation. Wraps send_message, receive_message, and delete_message. Paired with an in-memory implementation for tests.
app/store/dynamodb_store.py
The JobStore DynamoDB implementation. Owns the partition-key choice (UUID job_id), GSI query for idempotency keys, and update expressions for state transitions.
worker/runner.py
The poll loop: long-poll SQS → mark in_progress → run the handler → mark completed or failed → delete the message. Retry logic and DLQ handling live here.
app/job_processing.py
The pure handler functions (echo, sleep, fail, factorial). No I/O. Trivially unit-testable, easy to extend with new job types.
tests/test_sqs_dynamodb.py
End-to-end test against moto-mocked SQS + DynamoDB. Exercises the real boto3 code paths — same calls that run in production, just hitting moto's in-memory implementations.
03 · Flow · submit and process a job

One full job lifecycle — from the client's POST through the queue, into the worker, back to the client polling GET /jobs/{id} and seeing completed.

step 0 / 6
1

Client POSTs to /jobs

Body: {"type": "factorial", "payload": {"n": 10}, "idempotency_key": "abc"}. FastAPI validates with Pydantic.

2

Idempotency check (GSI query)

Producer queries the idempotency_key-index GSI. If a row exists with that key, the existing job_id is returned and the request becomes a no-op replay. Otherwise it continues.

3

Persist + enqueue

Producer PutItems a new row to DynamoDB with status pending and the payload, then SendMessages {job_id} to SQS. Returns 202 Accepted with the new job_id.

4

Worker pulls the message

The long-poll ReceiveMessage returns the job_id. SQS sets a 60-second visibility timeout — if the worker crashes mid-process, the message reappears.

5

Process + update state

Worker GetItems the row, marks in_progress, runs the handler in job_processing.py, then UpdateItems the row with completed + result JSON.

6

Delete the message

On success the worker DeleteMessages by receipt handle. Client now polls GET /jobs/{id} and gets status: completed, result: {...}. On failure, retry count bumps; after the cap, the message lands in the DLQ.

03 · Flow · toggle a task to done

A short user interaction traced from a checkbox click all the way to the backend PUT and back. Shows where state lives at each step.

step 0 / 5
1

User clicks the checkbox

The checkbox lives inside TaskItem.jsx. The onChange fires handleToggle, which calls the onToggle prop handed down from App. Local busy state flips to true; the row visually disables.

2

App.handleToggle decides the next status

App reads the current task's status. If it's done it'll flip to pending, otherwise done. Then it asks the service to persist that change.

3

tasksApi.update fires

The service layer issues http.put('/tasks/{id}', { status }). Any failure here is caught in App and surfaced via the ErrorBanner — the row stays at its old status, the user can retry.

4

Backend updates the row

FastAPI applies the partial update through SQLAlchemy, commits, returns the updated Task JSON. axios resolves the promise back in the browser.

5

State replaces the row

App's handler maps over tasks and swaps in the updated row. React re-renders TaskItem with the new status; the checkbox is now checked, the title gets the strike-through class. Counts on FilterBar update automatically via useMemo.

Project 04 · GenAI · Full-stack

GenAI Ad Creative Studio

A campaign workspace that turns a product brief into a draft creative set — headlines, descriptions, calls to action, and campaign concepts. The interesting design choice is the swap-in generation layer: a deterministic mock keeps the whole workflow runnable with zero credentials, and the same call site flips to a real LLM provider via httpx the moment two env vars are set. The output always comes back through a strict Pydantic schema, so the rest of the app never has to trust the model.

FastAPI React + Vite SQLite Pydantic httpx pytest Mock · Provider modes
README ↗ GitHub ↗
01 · Architecture

The React client owns the workspace UI. FastAPI owns campaign storage and orchestrates generation. The CopyGenerator is a thin strategy layer with two implementations — a local mock and a provider client — that both return the same CreativeSet shape. The LLM provider is dashed because it's optional: the system is fully usable without it.

in-repo module external store / service highlighted in the flow below
02 · Key files

Backend stays small: a route layer, a store, a generator. The frontend is one screen with three panels — list, brief, creative set — wired through a tiny fetch helper.

backend/app/main.py
Builds the FastAPI app via create_app(settings), mounts CORS, exposes the four routes, and translates generator failures into 503 (config) or 502 (provider) so the client always gets a clean error message.
backend/app/schemas.py
The Pydantic contracts. CampaignCreate validates the brief with field length bounds; CreativeSet defines the four-list output schema. Provider responses are validated against this same model — bad shapes raise GenerationProviderError.
backend/app/store.py
A small CampaignStore that owns the SQLite connection. UUID primary keys, ISO-8601 timestamps, and the creative set is serialized to a JSON column so the row stays self-contained.
backend/app/services/generation.py
The CopyGenerator strategy. Branches on GENERATION_MODE; _mock_creative_set returns a deterministic templated set keyed off the brief, _provider_creative_set POSTs the brief and an output schema to the configured endpoint and validates the response.
backend/app/config.py
Frozen Settings dataclass behind lru_cache. Reads DATABASE_URL, GENERATION_MODE, the three provider vars, and a comma-separated CORS origins list from the environment. Tests construct Settings directly to override.
frontend/src/App.jsx
One workspace screen: campaign rail on the left, brief form in the middle, creative set on the right. useEffect loads the list on mount; handleCreateCampaign and handleGenerate drive the two backend calls and keep local state in sync.
03 · Flow · brief to creative set

Walks one campaign from the empty form to a rendered creative set. Two backend round-trips — one to save the brief, one to generate the copy — and the generation step branches on the configured mode.

step 0 / 6
1

User fills the brief

Product name, product detail, audience, tone (one of five presets), and an objective. App.jsx holds the form in a single brief state object; the submit handler is the only place that triggers the first network call.

2

POST /api/campaigns

The createCampaign helper in api.js wraps fetch with JSON headers and a normalized error path. Pydantic's CampaignCreate rejects briefs that miss the length bounds with a 422 the UI surfaces inline.

3

Persist the campaign

CampaignStore.create_campaign mints a UUID, writes the row to SQLite with ISO timestamps, then reads it back so the response includes the assigned id. The creative set column starts NULL.

4

User clicks Generate

From the creative panel, the secondary button POSTs to /api/campaigns/{id}/generate. The route handler loads the campaign, raising 404 if the id is unknown, then hands the validated brief to the generator.

5

CopyGenerator picks a mode

In mock mode, the brief gets folded into a templated CreativeSet — three headlines, three descriptions, three CTAs, three concepts — and returns in microseconds. In provider mode, httpx POSTs the brief plus the expected output schema to the configured endpoint with a 20s timeout, and the response is model_validated back into a CreativeSet. Provider failures raise GenerationProviderError and the route returns 502.

6

Save and render

save_creative_set writes the JSON-serialized set back onto the same row and bumps updated_at. The route returns the full campaign; App.jsx swaps the updated record into its list and the creative panel re-renders four columns of copy.

Project 05 · C++ · systems engineering

C++ Matching Engine

A deterministic C++20 limit order book with price-time priority, integer tick prices, controlled concurrent ingestion, and a verification stack built to challenge correctness rather than merely demonstrate the happy path.

C++20 CMake GoogleTest Google Benchmark ASan · TSan libFuzzer
Architecture ↗ Performance ↗ GitHub ↗
01 · Architecture

The order book stays deliberately single-writer. Producers can submit concurrently, but one worker restores explicit ingestion order before touching the core engine. That keeps price-time behavior deterministic without spreading locks through a multi-step match.

→

→
Reorder bufferwindow + gap deadline
→
Single workernext contiguous sequence only
Matching workerexclusive mutation owner
→
MatchingEnginefills + trade sequencing
→
OrderBookordered levels + FIFO lists
→
Future resultacceptance, error, trades
in-process component active flow step

Failure policy: if an expected sequence stays absent past the configurable deadline, the facade fails closed, resolves buffered futures with one terminal error, and never executes later commands over the gap.

02 · Key files

The public surface is small; the interesting engineering is concentrated in the matching loop, coordinated book indexes, and the boundary that turns concurrent producers into one deterministic command stream.

src/matching_engine.cpp
Owns order and trade sequences. An incoming limit order repeatedly reads the best opposite order, executes at the resting price, applies partial or complete fills, emits exact trade records, and rests any remainder.
src/order_book.cpp
Coordinates three views: descending bid levels, ascending ask levels, and an average-constant-time active-ID index. FIFO lists provide time priority and stable iterators for cancellation.
src/concurrent_matching_engine.cpp
Restores explicit sequence order, limits reordering to a bounded admission window, owns the one-second default gap deadline, fails closed on missing input, and completes each producer promise.
include/matching_engine/thread_safe_queue.hpp
A bounded generic FIFO with blocking push/pop, deadline-aware pop, close semantics, and condition-variable wakeups. Producers sleep under backpressure; the worker never busy-waits.
tests/matching_engine_property_test.cpp
Runs 12,000 deterministic randomized commands against a deliberately simple independent matcher, comparing every trade field, full depth, best prices, active counts, and the uncrossed-book invariant after every operation.
fuzz/csv_command_fuzzer.cpp
Feeds arbitrary bytes through CSV parsing and command validation under libFuzzer, AddressSanitizer, and UndefinedBehaviorSanitizer. CI adds a short campaign to the 89-test suite.
03 · Flow · submit a crossing order

Follow one concurrently submitted order from producer admission through deterministic sequencing, matching, and its completed future. Use Step / Reset to highlight the active components.

step 0 / 6
1

Admission reserves the sequence

submit rejects zero, stale, duplicate, or too-distant ingestion sequences under a small state mutex. A valid command owns a promise before entering the bounded queue.

2

The queue applies backpressure

If capacity is full, the producer sleeps on not_full. The worker pops without spinning and moves out-of-order envelopes into an ordered map.

3

The sequencer protects history

The worker processes only the next contiguous value. A temporary gap may close before the deadline; a persistent gap stops admission and rejects buffered work rather than silently changing market history.

4

The incoming price crosses

The engine reads the best opposite order. While prices cross, it fills the smaller remaining quantity at the resting order's price, updating or removing that order through the book's stable index.

5

Trades become an exact result

Each fill receives a monotonic trade ID and sequence. Any incoming remainder rests on its price level; the trade vector moves into the producer's CommandResult.

6

The behavior is challenged from several angles

Named examples, exact integration scenarios, a reference model, fuzzing, strict warnings, clang-tidy, ASan/UBSan, TSan, and Release benchmarks all exercise the same library used by the CLI.

02 · Key files

FleetPulse is intentionally more than service code. The runbooks, architecture decisions, threat model, SLOs, failure drills, and committed evidence are part of the deliverable because operational behavior is a feature.

src/fleetpulse/agent/spool.py
A bounded SQLite spool keeps batches across restarts. Age and size limits prevent unbounded disk growth; explicit metrics record drops when the safety bounds are exhausted.
src/fleetpulse/agent/client.py
Sends stable batch IDs over HTTPS with request deadlines, capped exponential backoff, and full jitter. Replays preserve the same idempotency identity instead of manufacturing new work.
src/fleetpulse/api/routes.py
Authenticates and validates ingestion, then commits telemetry, the idempotency outcome, and an outbox event in one PostgreSQL transaction before acknowledging the agent.
src/fleetpulse/worker/relay.py
Finds unpublished outbox rows, publishes durable work to Redis Streams, records attempts, and can retry after Redis recovery without asking the API to recreate acknowledged data.
src/fleetpulse/worker/main.py
Runs consumer-group work with pending-message reclaim, bounded retry, dead-letter handling, and idempotent database transitions for fleet summaries and incident state.
evidence/INDEX.md + docs/runbooks/
Connects every reliability, performance, recovery, assistant-safety, and supply-chain claim to repeatable commands and preserved raw results. Targets, measurements, and projections stay explicitly labeled.
03 · Flow · durable telemetry to incident state

Trace one telemetry batch through a healthy run—and see why acknowledged work survives the failure of an asynchronous dependency.

step 0 / 7
1

Collect and spool locally

The container agent samples bounded CPU, memory, disk, process, socket, and network telemetry with psutil. It batches samples under a stable UUID and writes the batch to SQLite before attempting delivery.

2

Cross the only intended ingress

Nginx terminates local TLS, constrains the request, attaches or propagates a correlation ID, and load-balances to FastAPI. The API authenticates the agent and validates the bounded payload.

3

Commit the durable boundary

One PostgreSQL transaction writes the telemetry batch, its idempotency outcome, and an outbox row. Only after commit does the API acknowledge success; replaying the UUID returns the original outcome without duplicate telemetry.

4

Publish asynchronous work

The relay publishes unsent outbox rows to a Redis Stream. If Redis is unavailable, the row remains durable in PostgreSQL and a later relay attempt resumes—processing is delayed, not lost.

5

Process with recovery semantics

A consumer-group worker performs an idempotent transition, updates fleet summaries, and evaluates thresholds. It acknowledges only completed jobs; abandoned pending work can be reclaimed, and bounded failures reach a dead-letter stream.

6

Observe service and fleet health

Prometheus scrapes bounded-cardinality indicators, Grafana visualizes SLO health, and Alertmanager routes locally testable alerts. Controlled Redis and service failures verify both detection and recovery behavior.

7

Optional analysis remains read-only

An operator may send selected evidence to the disabled-by-default assistant. Secrets are redacted, every claim must cite supplied evidence, unsupported output abstains, and even an approved proposal has no execution path.

Solana Developer Passport

A verifiable learning portfolio deployed to Solana devnet. A browser wallet remains the authority, a Rust/Anchor program owns the rules, and deterministic Program Derived Addresses make each passport and milestone independently discoverable without a centralized database.

Rust · Anchor Solana devnet Program Derived Addresses TypeScript · React Solana Kit Wallet Standard LiteSVM

01 · Architecture

The frontend can read any address without a wallet. Writes are different: the connected wallet signs, Anchor verifies that signer against deterministic PDA seeds, and only then does the program create or mutate state. Private keys never enter the application.

Account model: one Passport PDA per authority stores identity metadata and a milestone count. Each evidence item lives in its own fixed-capacity Milestone PDA, avoiding repeated reallocation of one growing account and making duplicates impossible at the address level.

02 · Key files and trust boundaries

The client constructs the same deterministic addresses that the program validates, but the client is never trusted. All authority and size checks are repeated on-chain before state changes.

programs/developer-passport/src/lib.rs
Defines the deployed instruction surface: initialize a passport, record a milestone, update evidence, close a milestone, and close an empty passport. The declared program ID matches the live devnet account.
src/instructions/initialize_passport.rs
Requires a signing authority, pays rent from that signer, derives the only valid Passport PDA from [passport, authority], stores the bump, and rejects empty or oversized display names.
src/instructions/record_milestone.rs
Uses has_one and seed constraints to bind the Passport to its authority. The milestone ID becomes part of the PDA, while bounded title and evidence fields prevent account-size overflow.
src/state.rs + constants.rs
Calculates exact fixed account capacity, including Anchor discriminators and Borsh string prefixes. Display names cap at 32 bytes, titles at 64, and evidence URIs at 200.
apps/web/src/lib/passport.ts
Derives PDAs, Borsh-encodes instruction data, supplies Wallet Standard signer metadata, fetches base64 account data over RPC, and decodes Passport state without giving the application custody of keys.
programs/developer-passport/tests/passport.rs
Loads the compiled SBF program into LiteSVM and proves successful creation plus rejection of unauthorized writers, oversized names, and duplicate milestone PDAs. Live integration tests separately read the deployed accounts.
03 · Flow · wallet approval to public proof

Follow a learner from wallet discovery through a signed transaction and back to a decoded, Explorer-verifiable milestone. Use Step / Reset to highlight each boundary.

step 0 / 6
1

Discover, connect, and preserve custody

The Wallet Standard plugin discovers compatible browser wallets. Connecting exposes a public account and transaction signer—not a seed phrase or raw private key. Disconnecting removes the application session.

2

Derive the learner's unique Passport address

The client combines the constant passport seed with the authority public key and program ID. No server allocates IDs, and the same inputs always produce the same PDA.

3

Build and approve the transaction

The client Borsh-encodes the Anchor discriminator and bounded fields, adds the authority signer plus System Program and PDA accounts, and hands the complete transaction to the wallet for explicit approval.

4

Anchor revalidates every claim

The program checks that the authority signed, the Passport embeds that authority, the supplied PDA matches the expected seeds and bump, and the input fits the allocated account. Client-side correctness alone is never sufficient.

5

Record evidence in a separate Milestone PDA

The milestone ID joins the Passport key in a second deterministic address. Creating the same ID twice collides with the existing PDA and fails; a successful write stores title, evidence URI, timestamp, authority, and bump, then increments the Passport count.

6

Read back and verify independently

The React client fetches and decodes the account over devnet RPC. Explorer links expose the program, Passport PDA, Milestone PDA, and both creation transactions so the portfolio's core claims can be checked without trusting the UI.
